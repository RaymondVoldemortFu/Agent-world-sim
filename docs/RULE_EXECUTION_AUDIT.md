# 规则执行审计与修复

检查实验：`web-20260910-214817-0a123e91`，100天归档，读取MySQL决策、世界纪事和动作统计，未改写历史数据。

## 实验证据

- 第18天 E7777，云 #20：“七次了，field-0还是prepared，我手里0.86kg也没减——我承认自己光说不练。”
- 第10、11、19天等模型输出持续包含 `farm/grain/(5,5)` 目标，并公开承诺播种。发言是该次模型决策的原子动作，farm本应由后续规则继续执行。
- 全实验的动作时间表有10次clear，未记录sow、tend或harvest。
- 存档决策中1210次等待使用“完成日常需要，保留计划等待机会”。这一总数包含其他正常闲置，不能全部归因于播种缺陷。

## 根因与修复

播种规划只检查背包与地面的种子；不足时转入采办。采办却会把粮仓种子计入可用量，在原地判定材料已齐后返回空动作。控制器随后使用泛化等待，既未播种，也未报告阻断。底层sow本来允许直接消耗同格可用仓库的种子，因此这是规划层资源口径不一致。

修复后，播种规划与执行统一读取背包、地面和同格可用设施（condition>0.2）。同样对齐采办、制作、建筑材料与刻字的设施可用性，耕地工具检查也包含共有工棚。播种前检查季节；目标没有可执行步骤时保存并向模型提供goalBlocked，而不伪装成“日常完成”。已到达对象的meet目标正常结束。

另一个可观测性问题：提示词里的田地仅有id/crop/stage，持续播种期间仍为prepared，模型无法看见实际投入。现在同时提供面积、已投入种子、已完成／所需播种劳动、备地及收割劳动。语言宣称和个人判断仍不等于执行证据，以这些物理进度和事件结果为准。
