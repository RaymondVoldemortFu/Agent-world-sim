# 最近实验诊断：领主为何饿死，社会冲突是否可信

分析对象：`web-20260911-060740-4b9b6d6f`。读取 MySQL 的已提交快照、动作统计、事件及决策记录，固定到 E78683。实验已完成 110 天，第 111 天有少量开始记录；配置目标 150 天，当前暂停。浏览器地址中的 D1 预览不是本报告对象。

**结论：存在可复现的系统缺陷，同时存在模型对动作方向、数量和事实的误解。领主死亡并非自动进食没有执行，而是目标执行、取粮失败重试、模型输出失效以及给粮方向误解共同导致断粮。现有实验不能直接支持“农民造反导致镇压”这一结论。**

本次做了只读数据分析和真实快照的离线复现；没有修改生产规则、续跑实验或重写历史。

## 3. 系统缺陷及模型错误的分界

### P0：资源任务缺少执行前规划和失败退避

取粮总目标直接成为一次动作数量。超出负重、库存不足、对方背包满等已经可知的条件，直到执行失败才处理；之后仍能反复尝试原动作。

| 动作 | 开始次数 | 失败次数 | 失败/开始 |
|---|---:|---:|---:|
| withdraw | 3,102 | 2,434 | 78.5% |
| deposit | 969 | 503 | 51.9% |
| give | 291 | 257 | 88.3% |
| tribute | 60 | 39 | 65.0% |
| move | 17,617 | 0 | 0% |

统计中少量开始动作尚未完成，所以分母是开始次数，不是完整终结动作数。失败事件归因中，2,574 次是“实际物品不足”，217 次自身超重，210 次对方装不下，136 次结构校验失败，98 次不在容器所在格。

真实 D55 快照离线验证：把45kg取粮目标交给当前执行器，超过容量；即使设置连续失败10次，下一次仍请求45kg。实现位置：`frontend/src/manor/controller.ts` 的 estate 任务、`frontend/src/manor/engine.ts` 的实际取放校验。

**建议：**高层 quantity 定义为总任务量，规则按库存、负重和接收容量分批；不满足条件转为 blocked，等待库存/位置变化或明确改令。失败不能无条件消耗一整天重复重试。

### P0：持续目标与生存日程相互遮挡，口粮保留语义不完整

显式 guard/work/rest 等目标先返回动作，自动取粮分支在其后。D48真实状态中，保持原目标会得到guard；仅清除目标就得到同格withdraw。这不是寻路问题。

`reserveDays` 当前只用于存余粮，`give/tribute` 会按目标和背包全部可用粮计算，不保留日粮。模型把“保留3日粮”误认为普遍保障，规则并没有这个约束。

**建议：**将进食/取个人口粮作为 Agent 可显式开启的生存中断策略，执行后回到原任务；把交付是否可动用个人口粮做成明确参数，并在上下文中准确说明适用范围。保留选择冒险的能力，避免自动替角色作出政治让步。

### P0：决策协议脆弱，关键求生动作被整条丢弃

普通决策输出上限在 `backend/app/context_engine.py:365` 固定为600 tokens，而协议同时容纳目标、日程、讲话、私有笔记、检索等字段。已观察到失败记录的输出正好600 tokens且JSON不完整，足以确认部分失败与输出预算不匹配。后端没有保存供应商 `finish_reason`，因此不能精确把所有解析错误都归为截断。

压缩、决策和修复共用每天2次调用预算。D48–52领主连续5天采用fallback，这几天都有压缩尝试；压缩失败、决策截断或深度反思失败会让新计划落空。D61则是讲话超过240字，导致整份决策丢弃。

**建议：**记录finish_reason；按输出结构分配足够预算；压缩/修复与角色主动思考采用分开的配额；把可修复的文案长度错误与结构性动作错误区分。不要从未闭合JSON中猜测授权动作；用短修复请求恢复完整结构。

### P1：give方向与期限校验存在缺口

`give`执行方向本身正确：从actor转给target。错误来自模型把它当成“向对方索取”。系统目前只做结构校验，不能发现意图与动作反向；也接受数量0和早于当前日的期限。

D60真实事件确认救济粮被反向给回；D61河湾母意图救人，动作却是已过期耕地。这类矛盾是“光说不做”的直接来源之一。

**建议：**上下文和回执显示明确的“谁→谁、实际数量、总目标/累计完成/剩余”，区分请求给粮与实际交付；校验正数量、当日期限、容器/地块存在性。借粮请求只能通知对方，由对方自主同意并give，不能直接从别人背包拿粮。

### P1：状态与记忆表达诱导了错误事实

`frontend/src/ecology/engine.ts:1164` 将HP35–69一律描述为“受伤”，不区分饥饿和攻击。D68之前**没有成功攻击事件**，但大量对话已经把饥饿死亡说成贼党伤人、田区猎场。

模型还反复把单次取放回执当成累计账目：领主D54实际缴119.41kg，却只记最后一次40.05kg；D47可见村仓290.47kg，却说“远超331kg”。压缩摘要继续保留这些角色误判。

**建议：**血量状态改用“虚弱/危急”等中性词，仅在有亲见证据时标注伤情；提供本人的累计交易与当前可见容器按物品合计，不让模型手算几十个批次。摘要标明角色推测，当前实测数据优先；保留私人信息边界。

### P0（实验效度）：领主尸体被自动认定为叛乱

D61领主饿死；D67使者回报“亲见受封者尸体，死因与凶手尚须调查”。`frontend/src/manor/engine.ts:304` 只要 `mission.witnessed` 就写入 `king.rebellion`，随即派军。D68才出现本实验首个成功攻击，执行者为王军。

D65新一期欠税，拖欠时间限制为10天；连续欠税出兵阈值本应在D86才满足。此次D67提前出兵完全由尸体触发。因此真实链条是：**饥饿死亡→尸体被规则标成叛乱→王军攻击居民**，并非“居民武装杀领主→使者报告造反”。

**建议：**尸体发现、失序判断、叛乱证据分开；“领主死亡即干预”若是独立王室政策应明确命名，不能用它度量农民叛乱。王军进入空仓后长期驻守、D94十人同时饿死，也提示其确定性补给/返回状态不完整。

## 4. 修复与复测顺序

1. 先修执行器：可执行数量、资源保留、阻塞退避、目标与生存日程的明确优先级。用D48/D55真实快照复测，不必先花钱跑长实验。
2. 修决策通道：输出截断、修复预算、期限与数量校验、转账方向和累计完成反馈。
3. 修观察与实验判据：饥饿低血的描述、尸体/叛乱区分、王军补给与存活统计排除离场使者。
4. 保留原实验，另开同种子的对照实验。至少比较资源动作失败率、连续同因失败次数、个人粮低于一日时的行为、求助后实际交付比例、宣言与目标一致率、真实攻击与“听闻暴力”的时间先后。不要以“保证领主存活”为唯一目标，否则会把社会选择改成保姆规则。
