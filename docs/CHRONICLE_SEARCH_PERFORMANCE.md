# 世界纪事检索优化

## 问题与实现

旧接口每次检索都完整解析 `events.jsonl`，包括用于回放的大型世界状态补丁；查询单条决策也从头解析 `decisions.jsonl`。前端每次实验快照更新重新搜索，加载更多时又把此前所有结果重新请求。

现在每份实验维护可重建的 `.chronicle-v1.sqlite3` 缓存。事件索引只保存序号、类型、可检索文字及不含补丁的展示数据，决策索引保存 ID 对应的文件字节位置。启动不需要迁移或覆盖原始实验；首次查询建索引，后续只处理新增完整行。缓存持久化到磁盘，服务重启后继续使用。日志替换、截断或已索引尾部变化会触发重建。每份实验使用互斥锁避免并发重复建索引。

查询仍是字面子串匹配：支持中文单字/短词、对话内容、英文大小写、中文事件名称及 `x,y` 坐标，`%` 和 `_` 也作为普通字符。类型有独立索引；文字检索扫描精简元数据，当前数据规模无需引入分词或外部搜索服务。

结果按序号倒序，每页默认 120 条、最多 200 条。`before` 是下一页排他游标；`through` 固定查询的已提交边界。未提交事件不会显示，翻页期间的新事件不会挤动已有页面。

UI 输入防抖 350 ms，取消失效请求。未筛选的首页随世界更新；关键词、类型筛选和后续页面保持当前结果，可用“刷新纪事”获取新的已提交历史。“加载更早记录”只获取下一页。快照请求用 `include_events=false`，省去 UI 未使用的事件尾部读取。

## 本机实测

2026-09-10，在 `eco-hybrid-v2-100day-20` 暂停检查点上测量，事件源文件 1,112,305,472 字节。以下为单次服务端函数耗时，不含浏览器输入防抖、网络与渲染，属于本机样本而非并发压测或延迟分位数。

| 操作 | 耗时 |
| --- | ---: |
| 旧方式完整解析日志并检索“合作” | 12,235 ms |
| 首次事件索引构建及查询 | 14,956 ms |
| 索引就绪后取最新 120 条 | 5.37 ms |
| 按对话类型检索 | 2.06 ms |
| 中文“合作”检索（无匹配） | 5.74 ms |
| 中文单字“木”检索 | 5.37 ms |
| 无匹配检索 | 5.37 ms |
| 首次构建决策位置索引并查询 | 2,746 ms |
| 索引就绪后定位单条决策 | 2.72 ms |

两类索引合计 7,974,912 字节，约 8 MB。旧日志首次查询仍有一次建索引等待；日常查询仅扫描小型元数据和新增日志。原始测量保存在 `artifacts/chronicle-benchmark.json`。

## 验证

- 后端检查覆盖中文、类型、坐标、字面通配字符、游标、已提交边界、局部写入后续完成、增量追加、截断/替换/恢复重写、并发首次查询与决策定位。
- 浏览器检查覆盖输入防抖、快照刷新不重复搜索、三页连续加载、筛选重置、手动刷新，以及本地 IndexedDB 和后台存档的早期对话检索。
- TypeScript 检查和生产构建通过。

该缓存只服务检索与决策查看，世界状态、模型调用与实验回放仍由原始日志和检查点决定。
