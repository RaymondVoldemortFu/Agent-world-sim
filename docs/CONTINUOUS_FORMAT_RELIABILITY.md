## 压缩故障复现

领主上下文停留在第21天，长度约83,931估算 tokens。用副本复现旧压缩请求，模型再次输出了 `intent/task/routine` 计划而不是 `summary`。旧代码随后读取缺失的 summary 并丢失错误细节，因此压缩失败会持续阻断正常规划。

新压缩请求以固定压缩指令开头，将活动历史作为一个用户消息中的引用材料，并在最后明确索取摘要。真实模型输出通过摘要校验，随后计划通过引擎校验；该隔离样本压缩并补入新计划后约7,941估算 tokens。未将探针的输出写入实验角色上下文。

## 执行协议

- 网关通过本地 `POST /internal/validate-plan` 调用执行引擎的实际 parser，避免维护两套动作约束。本地 HTTP 客户端使用直连，避免 macOS 系统代理拦截回环请求。
- 每个阶段首次格式校验失败后最多纠正两次：保留相同请求前缀，在临时会话后附原回复和具体字段错误。规范化并通过校验的计划才进入长期会话历史。
- 超时、网络失败、408/429/5xx 最多重试两次，退避0.5秒、1秒。401等明确错误直接返回。
- 一次逻辑规划含压缩和纠错最多8次供应商尝试，整体截止150秒。这是单次失败恢复边界；不限制实验累计规划次数或 token 用量。
- 每次尝试保存阶段、原始正文、校验错误、规范化记录、结束原因、耗时与用量；最终结果按 requestId 缓存。世界结算仍使用原来的请求ID和计划版本校验，迟到结果不能覆盖更新的任务。
- 压缩仅在摘要通过校验后替换活动历史。格式纠错耗尽时保留旧历史；若上下文仍有空间，可以继续规划。固定前缀保持原样。
