# Agent 异步执行协议 v1（设计稿）

状态：协议设计完成，待实现。当前提交修复了领地动作的重复失败与王军执行器；当前运行器仍使用原批次调度，不应把本设计当作已经上线的并发能力。

## 目标与当前瓶颈

将“思考”“执行高层目标”“提交物理动作”分开。每个 Agent 有独立任务流；同一广场上的 Agent 可以同时请求 LLM。世界只对确实争用的资源做短暂互斥，模型网络等待不占用资源锁。

当前 `sim/scheduler.ts` 只取同一 readyAt 的连续 ID 前缀；遇到一个冲突角色就 break。喊话扩大到五格后，广场上的人几乎全被视为冲突。`scripts/simulate.ts` 又等待整个批次 `Promise.allSettled` 后按既定顺序提交，最慢请求拖住整批。核心问题是把可能变化的观察当作必须长时间锁定的事务。

最近实验有39,223个动作开始，其中大多数只是规则动作；模型调用2,665次。应首先让规则动作、网络请求与数据持久化解耦，而不是要求每个动作都通过一个异步LLM RPC。

验收目标：附近居民可同时思考；一次60秒模型超时不阻塞其他Agent执行；领地仓库不超卖；死亡后的响应不会复活Agent；重复返回或服务重启不会重复执行交付；所有实际结果可回放。吞吐提升通过基准测量，不预设倍数。

## 1. 单个 Agent 的三个状态机

| 层 | 状态 | 作用 |
|---|---|---|
| 思考 | idle / requested / ready / applied / superseded / failed | 一个Agent最多一个在途模型请求，同一时刻不同Agent可并发 |
| 高层目标 | active / blocked / completed / cancelled | 目标、剩余量和依赖条件跨多个物理动作保存 |
| 物理动作 | prepared / reserved / running / committed / rejected | 规则生成短动作，校验、预留、完成时结算 |

思考期间原来的自动进食、可执行日程或既有任务继续工作。收到新方案后在下一次动作边界替换旧方案，已经完成的动作不可撤回。首次思考尚无目标时执行已配置的进食日程或短等待。暴力、交付与新的政治承诺仍需要Agent明确下达的目标。

普通社交事件合并到Agent的待处理收件箱；死亡、目标失效、濒危和任务阻塞属于高优先级。一次阻塞变化触发一次重新规划机会，持续同一阻塞不反复调用模型。

## 2. 思考请求与计划提交

请求信封由后端生成，LLM只返回原有高层决策内容：

```ts
type ThinkRequest = {
  experimentId: string;
  requestId: string;                  // 幂等键，重试不换ID
  agentId: number;
  actorGeneration: number;            // 死亡/重建使旧请求失效
  baseSeq: number;                     // 输入观察的事件边界
  planVersion: number;
  contextHead: string;                 // 每个Agent的私有上下文链
  rulesVersion: string;
  issuedAtSimMinute: number;
  leaseUntilWallTime: number;          // 网络超时，与游戏日期分开
  budgetReservationId: string;
};
type PlanProposal = {
  requestId: string;
  decision: BrainOutput;
};
```

`baseSeq`用于说明结果依据的历史，不要求它等于最新全局seq。回复包含旧地图观察是正常情况。收到回复后：

1. 校验该请求是否仍属于当前Agent、当前计划世代，是否已消费，Agent是否存活且未离场。
2. 检查结构、当日期限、容器/地块ID、正数量与社交目标合法性；失败进入短修复或拒绝事件。
3. 将决策解释为对当前状态的**计划变更**。禁止把旧请求中的完整 `brainUpdate` 覆盖当前brain、背包、记忆、调用账单或时钟。
4. 保留期间新增的收件箱、真实任务回执和知识；记录 `PlanAccepted`，增加planVersion。
5. 规则执行器用当前位置、库存、负重重新导航和分批执行。普通移动或库存变化不必再花钱请求整个模型。

目标已死亡、所选容器不存在、命令因新一期税期含义改变等无法局部修正时，写入明确的拒绝原因，合并到下一次思考。发言中的过时主张保留为角色的主张，不能把它当作系统事实；真正发言时按当前位置确定听众。

## 3. 时间模型和公平性

v1采用单个权威世界时钟、离散事件队列和可配置的墙钟推进速率。一次推进只结算到下一物理动作完成或固定短时间片，不允许“只剩慢模型”时瞬间快进十个游戏日。

- LLM响应时间是墙钟时间；发言、进食、移动仍消耗游戏劳动分钟/AP。
- 思考期间旧计划继续执行，Agent不因网络等待被完全冻结。
- 每个在途请求有游戏时间最大陈旧度（建议初值120劳动分钟，可调）和墙钟租约；超期后允许旧日程继续，回复需重校验并在必要时重规划。
- 接受计划的生效时刻为当前模拟分钟与Agent下一动作边界的较晚者，绝不回写过去。
- 战斗和同格资源争用用 `(finishMinute, deterministicTieBreak, actionId)` 定序；同一时刻的顺序使用种子和动作ID，避免长期固定低ID优势。
- 日结是一条明确屏障：该日已开始动作须先终结或记录取消，未完成的模型请求可跨日返回并重新校验期限。日结不等待所有LLM。
- 增加最大步进/墙钟速率配置，记录实际生效时刻和迟到率。公平性评测单独注入不同网络延迟，观察它是否系统性改变某群体的生存和交付机会。

异步网络完成顺序可能改变一次新实验的行为；可回放性依靠记录实际接受顺序，不承诺相同seed配合不同网络延迟产生完全相同的新实验。离线确定性基准使用录制好的响应及生效时刻。

## 4. 资源冲突：锁短动作，不锁模型思考

每个资源有版本号。模型思考只读快照；物理提交由规则生成准确的读写集合。

| 操作 | 写入/预留资源 | 重校验 |
|---|---|---|
| 取粮 | 源容器可用批次、本人背包剩余容量 | 数量、门锁、当前站位 |
| 给粮 | 本人批次、接收方背包容量 | 双方距离、存活、授权目标 |
| 存粮 | 本人批次、目标容器 | 库存、位置、门锁 |
| 农活/收割 | 指定田条、收获量、背包容量 | 本月剩余劳动与成熟量 |
| 移动 | 本人位置、目的地通行条件 | 门锁、墙、区域；地块支持多人时不锁整格 |
| 攻击 | 攻击者/防御者战斗状态、撤退位置 | 双方存活、距离和本次策略 |
| 说话 | 本人时间、消息事件 | 提交时五格/一格听众；追加各自收件箱 |

仓库有10kg，甲乙各请求8kg：预留后一个获得8kg，另一个最多获得2kg，剩余目标进入blocked。不会先让两个模型串行，也不会等两个动作都失败后才重问模型。实际扣除在完成时发生；预留量单独记账，不能凭空消失。

预留只持续物理动作时长，按资源ID排序获取锁以避免死锁。动作取消、死亡、超时或恢复失败均释放预留。锁冲突不是Agent做错，不消耗额外模型调用；仅真正执行的动作计时，等待单列。

`blocked`保存原因、依赖资源和版本。资源版本不变时不重试；补货、腾出背包、门锁改变、目标进入范围或Agent修改目标后重新调度。每次重试有上限，竞争导致的短退避不应生成大量相同叙事日志。

## 5. 协议事件与回放

建议新增事件：`ThinkRequested`、`ThinkCompleted`、`PlanAccepted/Rejected`、`TaskBlocked/Unblocked`、`ActionReserved/Committed/Cancelled`。

物理提交结果统一携带：

```ts
type ActionResult = {
  actionId: string;
  taskId: string;
  agentId: number;
  status: 'completed' | 'partial' | 'blocked' | 'cancelled';
  from?: { kind: 'agent' | 'store'; id: string };
  to?: { kind: 'agent' | 'store' | 'crown'; id: string };
  item?: string;
  actualQuantity?: number;
  remainingQuantity?: number;
  reason?: string;
  seq: number;
};
```

固定规则、人格和配方知识继续位于缓存友好的固定前缀；观察增量、任务结果与未读消息追加到个人上下文。结果必须显式表示转账方向，累计值由账簿计算。每个Agent的contextHead以CAS更新；并发的是不同Agent的思考，不允许同一Agent分叉写入两段互不相知的历史。

## 6. MySQL 持久化与重启

新增 `think_requests`（requestId唯一、lease、budget、response）、`agent_plans`（agentId+generation、version、当前task）、`action_reservations`（资源与预留数量、到期、actionId）、`outbox`（待投递事件）。

一次提交在同一数据库事务内：校验版本→消费预留→更新Agent/容器→分配seq并保存精简回放delta→写outbox。模型调用在事务外完成。事件发布失败由outbox重投；消费方按事件ID去重。

采用单世界writer作为第一阶段实现，内存事务仍有短串行临界区；LLM、规则规划、查询和多个世界并发。数据库提交可批量刷盘，但UI只能看到已提交seq。不要先上多个共享世界writer，避免分布式死锁与回放不一致。

暂停：停止新思考与动作派发，已发出的付费请求结果落盘，物理动作保存剩余时间与预留。恢复：重建事件队列、校验租约、清理失效预留；已记录的响应无需再次付费，已经提交的交付不得重放第二次。

## 7. 调度、预算与接口

思考池设全局并发（初值8，可配）、每Agent在途上限1、每世界在途上限和供应商速率限制。优先级：紧急状态/阻塞变化、已收到的直接请求、常规思考、压缩与维护；加等待时间权重防止饥饿调度。

调用前原子预留模型请求和token预算。压缩/格式修复属于维护预算，与每日自主思考配额分开记录，同时受总费用上限控制。失败和丢弃回复也保留真实账单。日内短事件合并，避免每句喊话触发全部听众立即调用。

后端接口建议：

- `POST /experiments/{id}/think`：创建幂等请求，返回requestId。
- `POST /experiments/{id}/plans`：内部worker提交模型原始结果。
- `POST /experiments/{id}/actions`：内部执行器提交短动作/预留申请。
- `GET /experiments/{id}/stream`：SSE只推送已提交事件、队列与阻塞状态。

UI展示Agent当前任务、剩余数量、阻塞原因、正在思考/执行、模型延迟和全局在途请求数。不会把“模型已返回”显示成“动作已完成”。

## 8. 实施切分与验证

1. 抽出 `PlanProposal → 当前状态校验 → task`，逐步替代携带整份旧brain的Decision提交。增加任务进度与阻塞依赖。
2. 将run loop中的整批等待换成持久化思考池；先单writer，使用完成队列逐个接收回复。保留旧调度器作为对照。
3. 增加资源预留与版本提交，删除按潜在五格喊话范围阻止并发思考的限制；聊天改成事件投递。
4. 加入崩溃恢复、预算预留和公平性观测后，再提高并发上限。

必测：同仓超额取粮、相互给粮不死锁、目标在等待中死亡/走远、迟到回复撞上新计划、重复回调、暂停恢复、数据库提交成功但客户端断线、模型超时而其他Agent继续执行、跨日过期、喊话听众变动、日结与动作同时完成。每项验证库存守恒、非负AP、提交幂等、世代一致、事件回放hash一致。

基准使用最新实验的真实状态、固定响应与注入延迟，比较并发1/4/8/16：每分钟完成模型请求、有效动作/秒、p50/p95延迟、阻塞率、条件不变时重试数、上下文重建/丢弃率、费用、不同网络延迟Agent的机会差异。随后再做100天付费对照实验。
